## A tool is one object

Agents commonly end up with the same shape. A tool is a single value holding four things: a **name**, a **description**, an **input schema**, and an **executor** (the function that does the work). Compare Thorsten Ball's Go agent with OpenCode's `read` tool:

```go
// Thorsten Ball (Go)
type ToolDefinition struct {
  Name        string
  Description string
  InputSchema ToolInputSchemaParam
  Function    func(input json.RawMessage)
                (string, error)
}
```

```ts
// OpenCode read tool (TS + Effect)
editor.add({
  name,             // "read"
  description: "Read the contents of…",
  input: Input,     // Effect Schema
  output: Output,
  execute: (input, context) => …,
})
```

Sources: [How to Build an Agent](https://ampcode.com/how-to-build-an-agent); [packages/core/src/tool/plugin/read.ts](https://github.com/anomalyco/opencode/blob/863ea41364/packages/core/src/tool/plugin/read.ts). OpenCode's [tool/AGENTS.md](https://github.com/anomalyco/opencode/blob/863ea41364/packages/core/src/tool/AGENTS.md) makes this a rule: "Each tool carries its name, options, schemas, and executable behavior in one object."

Notice that neither object mentions a protocol. A tool is provider-neutral. Keeping it that way is what makes tools _data_:

1. **Each protocol's tool list is derived from the registry.** One small function turns a tool into `{ type: "function", function: { name, description, parameters } }` for OpenAI; another turns it into `{ name, description, input_schema }` for Anthropic. Same JSON Schema, different wrapping. You never write a definition twice.
2. **Dispatch is a lookup by name.** When a tool call arrives, find the tool with that name and run its executor. A tool the model asks for that you don't have isn't a crash either: Ball's agent replies `"tool not found"` as an error result.

Add a fifth tool and you add one object. Neither loop changes, and neither does any protocol code. This is the main result of this Part.

## Three rules for tools the model can use well

### 1. Descriptions matter most

Claude's docs call detailed descriptions ["by far the most important factor in tool performance"](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools) and recommend at least 3–4 sentences: what the tool does, when to use it (and when not to), what each parameter means, and its limits. OpenCode's `read` description is seven sentences long, and it tells the model how to read large files ("Use offset and limit…") and when to use a different tool ("use grep to find specific content"). Anthropic's tool-design post gives a useful test: describe the tool [as you would to a new hire](https://www.anthropic.com/engineering/writing-tools-for-agents). The advice comes from Anthropic, but it matters _more_ for a 9B local model, which has less ability to guess what you meant.

### 2. Errors should say what to do next

The docs: "Instead of generic errors such as `"failed"`, include what went wrong and what Claude should try next." Here is OpenCode doing it. When a file is missing, the `read` tool doesn't return "not found". It looks for similar names:

```text
File not found: docs/README

Did you mean one of these?
docs/README.md
```

Its truncation notice works the same way: `[Output truncated. Continue reading with offset: 2001]`. The model gets the exact next call to make. On your local providers, where there's no error flag, this text is everything.

### 3. Model input is untrusted

The schema tells the model what to send, but nothing forces it to comply. Claude's docs say that when input is invalid and you reply with an error result, "Claude will retry 2–3 times with corrections before apologizing to the user." Local models make this mistake more often, and the OpenAI protocol adds one more way to fail: `arguments` arrives as a JSON _string_, so `JSON.parse` itself can throw on a malformed reply. Treat a parse failure like any other bad input: an instructive error result, never a crash. OpenCode's registry validates model input at runtime for every tool ([tool/AGENTS.md](https://github.com/anomalyco/opencode/blob/863ea41364/packages/core/src/tool/AGENTS.md), Registration). In Part 5 (_Why Effect: errors as values_), `Schema` will do this for you. For now, check it by hand.

## Tools on each provider

### Ollama and llama.cpp (OpenAI protocol)

| What       | Shape                                                                              |
| ---------- | ---------------------------------------------------------------------------------- |
| Definition | `{ type: "function", function: { name, description, parameters } }`                |
| Call       | `message.tool_calls[i]`: `id`, `function.name`, `function.arguments` (JSON string) |
| Result     | `{ role: "tool", tool_call_id, content }`, one message per call                    |
| Failure    | No flag. Start the content with `Error:` and say what to try next.                 |

- **Keep the tool list short.** Every definition costs context on every step, and a 32k window is small. Anthropic's tool-design advice ("more tools don't always lead to better outcomes") applies even more strongly here.
- **llama.cpp picks a tool-call format from the model's chat template.** When it doesn't recognize the template it falls back to a generic format that "may consume more tokens and be less efficient" ([function-calling.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md)). If tool calls misbehave on llama.cpp but not Ollama, check the chat format in the server's startup log.
- **Ollama's OpenAI endpoint doesn't support `tool_choice`**, so you can't force a tool call there ([OpenAI compatibility](https://docs.ollama.com/api/openai-compatibility)). Steer with the prompt and descriptions instead.

### Claude (Anthropic protocol)

| What       | Shape                                                                                          |
| ---------- | ---------------------------------------------------------------------------------------------- |
| Definition | `{ name, description, input_schema }`                                                          |
| Call       | `content[i]` with `type: "tool_use"`: `id`, `name`, `input` (an object)                        |
| Result     | One user message whose content starts with every `tool_result` block: `tool_use_id`, `content` |
| Failure    | `is_error: true`, plus the same instructive text                                               |

Two Claude-only extras: `strict: true` on a tool definition makes Claude's calls always match your schema ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)), and Claude is your reference. When a local model keeps calling a tool wrong, run the same prompt and tools against Claude. If Claude gets it right, improve the description or accept the model's limit. If Claude gets it wrong too, the problem is probably your definition or your dispatch.

#### Step 1: Make `execute` take `unknown`

Part 1 left `execute` taking `any`, which lets code read fields of the model's input without checking them. With `unknown` the compiler rejects that. Replace the `Tool` type:

```ts
type Tool = {
  name: string
  description: string
  parameters: Record<string, unknown> // JSON Schema, shared by both protocols
  execute: (input: unknown) => Promise<string>
}
```

Bun runs a file without type checking, so use the compiler to see the effect:

```bash

```

It reports three errors, one per tool, each saying that `unknown` is not assignable to the destructured parameter, for example `Type 'unknown' is not assignable to type '{ path: any; }'`. The three `execute` functions destructure fields out of input they have not checked. Step 2 fixes them.

#### Step 2: Check input by hand

Every tool needs the same check: is the field there, and is it a string? One helper does it and writes the error message the model will read. Add it above `listFiles`:

```ts
// Reads one string field from model input, or throws a message that says how to fix it.
const field = (input: unknown, key: string, example: string): string => {
  const value = typeof input === "object" && input !== null ? (input as Record<string, unknown>)[key] : undefined
  if (typeof value !== "string") throw new Error(`${key} must be a string, e.g. ${example}`)
  return value
}
```

The third argument is an example that ends up in the message, for instance `path must be a string, e.g. src/index.ts`. Now make each tool read its fields through `field`. In the `list_files` entry, replace the `execute` line:

#### Step 3: One function that never throws

`runTool(name, rawArguments)` is the single place where a tool call turns into a result. It takes the tool name and the arguments exactly as the model sent them (on the OpenAI protocol, a JSON string) and always returns `{ content, isError }`. An unknown tool, invalid JSON, invalid input and an executor that throws all come back as an error result instead of ending the program. Add it below the `tools` array and above `toOpenAITool`:

```ts
type ToolResult = { content: string; isError: boolean }

// Never throws: every failure becomes a result the model can read.
const runTool = async (name: string, rawArguments: string): Promise<ToolResult> => {
  try {
    const tool = tools.find((tool) => tool.name === name)
    if (!tool) throw new Error(`Unknown tool: ${name}. Available tools: ${tools.map((tool) => tool.name).join(", ")}`)

    let input: unknown
    try {
      input = JSON.parse(rawArguments)
    } catch {
      throw new Error(`The arguments are not valid JSON: ${rawArguments}`)
    }

    return { content: await tool.execute(input), isError: false }
  } catch (error) {
    return { content: error instanceof Error ? error.message : String(error), isError: true }
  }
}
```

Then replace the four lines in the loop that looked up the tool, threw for an unknown one and ran it. This is also where the `Error:` prefix is added, because this protocol has no error flag and the text is the only signal:

Replace this:

```ts
      const tool = tools.find((tool) => tool.name === call.function.name)
      if (!tool) throw new Error(`The model asked for an unknown tool: ${call.function.name}`)
```

With this:

#### Step 4: Add `write_file` and `bash`

First the import, added at the top of the file with the others:

```ts
import { execFile } from "node:child_process"
```

Then two functions, placed above the `tools` array:

```ts
const saveFile = async (path: string, content: string) => {
  await mkdir(dirname(path), { recursive: true })
  await writeFile(path, content)
  return `Wrote ${content.length} characters to ${path}`
}

const TIMEOUT_MS = 30_000
const MAX_OUTPUT = 10_000

const runBash = (command: string) =>
  new Promise<string>((resolve, reject) => {
    execFile("bash", ["-c", command], { timeout: TIMEOUT_MS, maxBuffer: 10_000_000 }, (error, stdout, stderr) => {
      if (error?.killed) return reject(new Error(`The command ran longer than ${TIMEOUT_MS} ms and was stopped. Try a faster command.`))
      if (error && typeof error.code !== "number") return reject(error)
      const output = `${stdout}${stderr}`
      const shown =
        output.length > MAX_OUTPUT
          ? `${output.slice(0, MAX_OUTPUT)}\n[Output truncated after ${MAX_OUTPUT} characters. Filter it with head, tail or grep.]`
          : output
      resolve(`Exit code: ${error ? error.code : 0}\n${shown}`)
    })
  })
```

`runBash` makes four decisions that determine what the model sees:

- The result starts with `Exit code: N`, so cutting long output cannot hide it.
- A non-zero exit is an ordinary result, not an error result. `grep` exits with 1 when nothing matches, and the model can read the code itself. OpenCode's [shell tool](https://github.com/anomalyco/opencode/blob/863ea41364/packages/core/src/tool/plugin/shell.ts) also returns output normally and records the exit code alongside it.
- A command that runs past 30 seconds is stopped and reported as an error result that says so. A failure to start `bash` is an error result too.
- Output beyond 10,000 characters is cut, with a notice that says how to filter it.

Then add two entries at the end of the `tools` array, after `edit_file`:

```ts
  await writeFile(path, content.replace(oldStr, () => newStr))
  return "OK"
}
```

> **Watch for this.** With five tools, a model may request several tools in one reply. Every call needs its own result. On the OpenAI protocol that's one `role: "tool"` message per call, right after the assistant message. On Anthropic it's one user message whose content [starts with all the `tool_result` blocks](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls). A 400 error mentioning "tool_use ids were found without tool_result blocks" indicates the results were not formatted as above.

> **If you have 32 GB or more of memory.** A larger local model tends to make fewer malformed calls, and can serve as a free second reference before using Claude. Keep building against `qwen3.5:9b`: code that handles a small model's mistakes also handles larger models'.

> **Result.** Adding a tool now means adding one object, and it works on every provider at once. Your tools no longer depend on your loops, and that independence is what lets OpenCode accept tools from plugins and MCP servers it has never seen.
