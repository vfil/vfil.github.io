## Foreword

This Part separates accepting a prompt from running it. Each line the user types is saved in the SQLite file from [Part 8](/posts/the-session-as-an-event-log/) as soon as it is read, and the agent runs it later, when it is free. A prompt typed while a turn runs waits its turn, and one that is still waiting when the process is killed is there on the next start. It is the second Part of Stage B (Session) in [the roadmap](/posts/the-roadmap/).

The code for this Part is available as the [`Part9_inbox_vs_execution` snapshot of vfil/sigma-agent](https://github.com/vfil/sigma-agent/tree/Part9_inbox_vs_execution), the repo where I build this agent in parallel.

## A prompt typed while the agent is busy

Suppose the agent is in the middle of a refactor. It has read a dozen files, edited three of them, and started the test suite, which will take a few minutes. While it works, the user remembers one more thing and types a second line: "also update the changelog". A moment later the terminal is closed, or the laptop goes to sleep and the process is killed.

With the agent from [Part 8](/posts/the-session-as-an-event-log/), that second line is gone. Nothing was reading the keyboard while the turn ran, so the line was sitting in the terminal's own input buffer, outside the program. The log from [Part 8](/posts/the-session-as-an-event-log/) is durable, but it starts at the moment the agent takes a prompt. Everything the user handed over before that moment depends on the process staying alive.

This Part changes where a prompt is kept first. A prompt is meant to be safe from the moment the user hands it over, whether or not the agent can do anything with it yet. A mail slot in a door works this way: a letter that drops through the slot is delivered, whether or not anyone is home to read it, and reading it is a separate act that happens later. For the agent, _accepting_ a prompt becomes its own step, a write to the SQLite file, and _running_ a prompt becomes a second step that starts when the agent is free. OpenCode's AGENTS.md states the rule as "Keep durable prompt admission separate from model execution" ([AGENTS.md](https://github.com/anomalyco/opencode/blob/97be25f046/AGENTS.md#L208)).

### Why this belongs to the session

Anthropic's article on [Managed Agents](https://www.anthropic.com/research/managed-agents), which [Part 2](/posts/the-roadmap/) introduced, describes the session as "the append-only log of everything that happened", kept apart from the harness, the loop that calls the model. Because the log sits outside the harness, the article says, "nothing in the harness needs to survive a crash": a new one can be started, read the log and "resume from the last event". [Part 8](/posts/the-session-as-an-event-log/) built that log for what the agent did. This Part applies the same thought to what the user asked.

The other article cited in [Part 1](/posts/the-loop/), [Building effective agents](https://www.anthropic.com/research/building-effective-agents), notes that agents "can pause for human feedback at checkpoints or when encountering blockers". Human input arrives at the human's pace and not at the agent's. A user may type while a tool runs, think of a correction a minute after pressing Enter, or send three requests in a row. For an agent that listens only between turns, each of those is a chance to lose the line. An agent with an inbox keeps the line.

### What a restart finds today

This table lists the places a prompt can be when the process dies, and what the next run finds:

| The prompt is...                                | It lives in...              | The next run...                                                   |
| ----------------------------------------------- | --------------------------- | ----------------------------------------------------------------- |
| typed while a turn runs                         | the terminal's input buffer | never sees it                                                     |
| read by the program, not yet appended           | the process's memory        | never sees it                                                     |
| appended as a `prompt` event, turn not finished | the file                    | finishes the turn ([Part 8](/posts/the-session-as-an-event-log/)) |

The first two rows are the ones this Part changes. The second row is a short gap: between the moment the program has the text in memory and the moment the `prompt` event is in the file, one insert wide, but it is there. After this Part, the first two rows end up in the same place as the third: in the file, where a restart can find them.

The agent changes in four places. A new table holds the prompts that wait. The session gets methods to put a prompt into it and take one out. The terminal learns to share the keyboard between two readers. And the REPL, the read-eval-print loop that reads a line, runs a turn on it, prints the output and asks again, splits into a reader that accepts prompts and a worker that runs them.

## The inbox

### Four words

Four terms are used from here on. The _inbox_ holds the prompts a session has accepted and not yet run, oldest first. To _admit_ a prompt is to put it into the inbox. To _deliver_ a prompt is to move the oldest one out of the inbox and into the event log as a `prompt` event, which starts a turn. A _wake_ is a signal that tells the agent to look at the inbox. A prompt is always in exactly one of two places, the inbox or the event log, and never in both.

### Six decisions in the design

### 1. A prompt is in the inbox or in the log, and the log keeps its meaning

The event log from [Part 8](/posts/the-session-as-an-event-log/) records facts that happened: the user said this, the model answered that. A prompt that waits has not been answered by anyone yet, so it is not that kind of fact. The inbox is a second table with one row per waiting prompt, and a row is deleted when its prompt is delivered. The table is a to-do list, and the log is the record of what was done.

The other way to do this is to add two events to the log, "prompt queued" and "prompt delivered", and work out the waiting prompts by folding the log. That would need no second table. It would also make accepting a prompt a write to the log, whose event numbers are counted by one writer ([Part 8](/posts/the-session-as-an-event-log/)), and it would put prompts in the log that the model has not yet seen. OpenCode keeps a separate table for the same reason. Its AGENTS.md says: "`Session.prompt(...)` publishes `session.inbox.enqueued`, whose projection inserts one durable `session_inbox` row [...] `session_inbox` stores only unconsumed work" ([AGENTS.md](https://github.com/anomalyco/opencode/blob/97be25f046/AGENTS.md#L208)).

### 2. Delivery is one transaction

Delivering a prompt takes two statements: delete the row from the inbox, and insert the `prompt` event into the log. A _transaction_ is a group of statements that SQLite applies as a whole or not at all, even if the process is killed in the middle. Without one, a kill between the two statements has two possible outcomes. If the delete came first, the prompt is in neither place and is lost. If the insert came first, the prompt is in both and runs twice.

With the two statements in one transaction, the prompt is in the inbox or in the log at every moment. OpenCode does the same with its own tables: "Delivery publishes `session.inbox.delivered`; its projection consumes the inbox row and inserts the visible message in the same transaction" (same paragraph of AGENTS.md).

### 3. The wake is a hint, and the inbox is the truth

When a prompt is admitted, the code that runs prompts has to find out. That is the job of the wake. The wake carries no prompt. It means "look at the inbox", and the prompt itself is in the table. Two consequences follow. Several wakes in a row can be merged into one, because the worker reads the inbox until it is empty anyway. And a missed wake delays a prompt at most until the next look, because the worker looks again after every turn, and at startup it looks at everything that was left behind.

OpenCode uses the same word and the same idea. Its execution service has a method `wake` with the comment "Registers newly recorded work. Repeated wakeups may coalesce" ([session/execution.ts](https://github.com/anomalyco/opencode/blob/97be25f046/packages/core/src/session/execution.ts#L24-L25)). In the agent here the wake is a small Effect `Queue` that holds at most one item.

### 4. One prompt per turn, oldest first, and only when the agent is idle

The worker delivers a prompt only after the previous turn has ended. A prompt typed in the middle of a turn waits, so the model never finds a new user message in the history halfway through its own work. OpenCode names this delivery mode "queue". It has a second mode, "steer", that delivers a prompt at a step boundary inside a running turn, and in OpenCode prompts steer by default ([AGENTS.md](https://github.com/anomalyco/opencode/blob/97be25f046/AGENTS.md#L214), [session/inbox.ts](https://github.com/anomalyco/opencode/blob/97be25f046/packages/core/src/session/inbox.ts#L52-L57), [the two modes](https://github.com/anomalyco/opencode/blob/97be25f046/packages/core/src/session/inbox.ts#L262-L279)). The agent here has only the first mode.

### 5. A reader and a worker

The REPL splits in two halves that do not wait for each other. The _reader_ asks for a line, admits it, rings the wake and asks again. It never waits for the model. The _worker_ first finishes an interrupted turn, the way [Part 8](/posts/the-session-as-an-event-log/) does, and then repeats: deliver the oldest prompt, run its turn, and when the inbox is empty wait for a wake.

Each half runs as a _fiber_, which is Effect's lightweight thread: an independent task that the runtime pauses while it waits for something and resumes later. The program ends when the input has ended and the inbox is empty, so the worker finishes the queued prompts first. One detail matters for that rule. The worker reads the flag "input has ended" before it delivers. If it read the flag after, a prompt admitted just before the end could be missed: the delivery finds the inbox empty, the reader admits the last prompt and ends the input, and the worker sees the flag set and quits without running it.

### 6. The terminal gives each line to the newest question

Two places in the agent can now ask the user something at the same time: the reader, with `You: `, and a tool that needs approval, with `Allow: ... [y/N]`. The terminal from [Part 8](/posts/the-session-as-an-event-log/) used readline's `question` for both, and two things happen with that under Bun 1.4.4. When two questions are open, the first line typed goes to the older one, so a `y` meant for the approval would be admitted as a new prompt. And a line that arrives while no question is open is dropped, so when several lines are piped in, only the first one is read.

A small router, `makeLines`, replaces that. It keeps lines that nobody has asked for yet, hands a line to the newest open question (the one printed last is the one the user is answering), and fails all open questions when the input ends. The `Terminal` service keeps the same three methods, so nothing that uses it changes.

### What this leaves for later

A prompt that always kills the process is delivered once and then resumed on every start, so the agent can crash in a loop. The `resume` from [Part 8](/posts/the-session-as-an-event-log/) has the same limit. A line typed while the model is streaming appears after the `You: ` prompt that is already on screen, in the middle of the reply. Steering a running turn is not built. And a session never shrinks, so a long task will eventually outgrow the model's context window, which the roadmap's _Context limits and compaction_ covers.

### Step 1: The inbox table

[Part 8](/posts/the-session-as-an-event-log/) kept the event table in `src/session-table.ts`. The file is about to hold two tables, so the singular name no longer fits. The file moves to `src/db/schema.ts`.

The move touches three places. The file changes folder, the import in `src/session.ts` follows it, and the config tells Drizzle Kit where to look. First, in the `my-agent` folder, move the file:

```bash

```

Next, in `src/session.ts`, find the import of the table file near the top. It currently reads `import { EventTable } from "./session-table"`. Replace that line with:

```ts

```

Last, open `drizzle.config.ts` in the project folder, next to `package.json`. It exists from [Part 8](/posts/the-session-as-an-event-log/). Replace its contents with the version below, in which only the `schema` line is different:

```ts
import { defineConfig } from "drizzle-kit"

export default defineConfig({
  dialect: "sqlite",
  schema: "./src/db/schema.ts",
  out: "./drizzle",
})
```

1. `src/db/schema.ts` holds the same `EventTable` as before. Only the folder and the file name change.
2. `src/session.ts` imports from `./db/schema`. It already imports `EventTable`; `InboxTable` is added to the same line, since Step 2 uses it.
3. `schema` in `drizzle.config.ts` is the path Drizzle Kit reads the tables from. It takes a file, a folder or a glob, so a project with many tables can later point it at a folder instead.
4. The first migration is not affected. Drizzle Kit stores the table definitions in its snapshots, not the path of the file they came from, so generating a migration after the move reports no schema changes.

The inbox is declared next to the event table. Open `src/db/schema.ts` and add this at the bottom of the file, after `EventTable`. The imports at the top already cover it. Each row is one waiting prompt:

```ts
// The inbox: the prompts a session has accepted and not yet run. A row is deleted when its prompt is delivered.
// `id` counts up, so the lowest id is the oldest prompt.
export const InboxTable = sqliteTable("inbox", {
  id: integer().primaryKey({ autoIncrement: true }),
  session_id: text().notNull(),
  text: text().notNull(),
})
```

1. `InboxTable` is a second table in the same SQLite file as `EventTable`, so one transaction can touch both.
2. `id` is an integer that the database fills in and counts up (`autoIncrement`). Because it only grows, the row with the lowest `id` is the oldest prompt, and that is the order of delivery.
3. `session_id` says which session the prompt belongs to, as in the event table, so one file can hold the inboxes of several sessions.
4. `text` is the prompt itself. There is no column for a time or a status: a row exists while the prompt waits, and it is deleted when the prompt is delivered.

Drizzle Kit compares the declared tables with the last snapshot and writes only the difference. Run the generator from the `my-agent` folder, and name the migration `inbox`. The command creates a new folder under `drizzle/` and writes the SQL file for you, so there is nothing to type into it. The first migration stays as it was:

```text
$ bun run db:generate --name inbox
$ drizzle-kit generate --name inbox
No config path provided, using default 'drizzle.config.ts'
Reading config file '/path/to/my-agent/drizzle.config.ts'
[✓] Your SQL migration ➜ drizzle/20261111091451_inbox/migration.sql 🚀
```

The generated file `drizzle/20261111091451_inbox/migration.sql` contains:

```sql
CREATE TABLE `inbox` (
	`id` integer PRIMARY KEY AUTOINCREMENT,
	`session_id` text NOT NULL,
	`text` text NOT NULL

```

The folder name starts with the time of generation, so it differs from run to run. The migrations run in that order when the agent opens the file, so a database written by [Part 8](/posts/the-session-as-an-event-log/) gets the new table the first time Part 9 opens it, and keeps its events.

### Step 2: Admit, deliver and pending

The agent needs three new things from its session. All of the changes in this step are in `src/session.ts`, which exists from [Part 8](/posts/the-session-as-an-event-log/). First, in the import from `drizzle-orm` near the top, add `count` to the list, since `pending` uses it:

```ts
import { asc, count, eq, max } from "drizzle-orm"
```

Next, find the `Session` class and replace it, comment and all, with the version below. It is the service definition with the three new members and what each promises:

```ts
// What the agent needs from its session: accept prompts, append facts, and read the facts back.
export class Session extends Context.Service<
  Session,
  {
    readonly id: string
    // Saves a prompt in the inbox. From this moment it survives a restart, whether or not the model ever sees it.
    readonly admit: (text: string) => Effect.Effect<void>
    // Moves the oldest prompt out of the inbox and into the log as a `prompt` event, in one indivisible act.
    // Returns its text, or undefined when the inbox is empty.
    readonly deliver: Effect.Effect<string | undefined>
    // How many prompts wait in the inbox.
    readonly pending: Effect.Effect<number>
    readonly append: (event: SessionEvent) => Effect.Effect<void>
    // Every call reads the log again.
    readonly events: Effect.Effect<SessionEvent[], SessionCorrupt>
    readonly history: Effect.Effect<Message[], SessionCorrupt>
  }
>()("@agent/Session") {}
```

1. `admit` takes the text of a prompt and writes it to the inbox. When the Effect has finished, the prompt is in the file. Nothing in its type can fail, because a disk failure is a defect, as it is for `append`.
2. `deliver` is an Effect and not a function. Each time it runs, it moves the oldest prompt of this session from the inbox to the log and returns its text, or returns `undefined` when there is nothing to deliver.
3. `pending` counts the rows in the inbox of this session. The agent uses it once, at startup, to tell the user what an earlier run left behind.
4. The rest of the service is as in [Part 8](/posts/the-session-as-an-event-log/). The comments on the three new members are the contract the tests in step 3 check.

The implementation is also in `src/session.ts`, inside the generator of `SessionLive`. First, find the line `const thisSession = eq(EventTable.session_id, options.id)` and add a second condition right below it, for the rows of this session's inbox:

```ts
      const thisInbox = eq(InboxTable.session_id, options.id)
```

Then find the line `return Session.of({ id: options.id, append, events, history: Effect.map(events, toHistory) })` at the end of the generator. Replace that one line with the code below, which defines the new pieces first and then returns the service with the three new members added:

```ts
      const admit = (text: string) =>
        db.insert(InboxTable).values({ session_id: options.id, text }).pipe(Effect.asVoid, Effect.orDie)

      // Deleting the inbox row and inserting the `prompt` event happen in one transaction: both take effect,
      // or neither does. A crash between the two statements cannot lose the prompt or deliver it twice.
      const deliver = Effect.suspend(() => {
        const next = seq + 1
        return db
          .transaction((tx) =>
            Effect.gen(function* () {
              const [oldest] = yield* tx.select().from(InboxTable).where(thisInbox).orderBy(asc(InboxTable.id)).limit(1)
              if (!oldest) return undefined
              yield* tx.delete(InboxTable).where(eq(InboxTable.id, oldest.id))
              yield* tx
                .insert(EventTable)
                .values({ session_id: options.id, seq: next, type: "prompt", data: encode({ type: "prompt", text: oldest.text }) })
              return oldest.text
            }),
          )
          .pipe(
            // The number is used up only once the transaction has committed.
            Effect.tap((text) =>
              Effect.sync(() => {
                if (text !== undefined) seq = next
              }),
            ),
            Effect.orDie,
          )
      })

      const pending = db.select({ waiting: count() }).from(InboxTable).where(thisInbox).pipe(
        Effect.map(([row]) => row?.waiting ?? 0),
        Effect.orDie,
      )

      return Session.of({ id: options.id, admit, deliver, pending, append, events, history: Effect.map(events, toHistory) })
```

1. `thisInbox` is the condition "this session's rows", defined once like `thisSession` and used by the queries on the inbox.
2. `admit` is one insert. The id and the order come from the database.
3. `deliver` starts with `const next = seq + 1`, the number the new `prompt` event will have. The counter itself is not moved yet.
4. `db.transaction` runs the generator it is given inside a SQLite transaction. The generator reads the oldest inbox row of this session, deletes it, inserts the `prompt` event with the number `next`, and returns the text. If the inbox is empty it returns `undefined` and changes nothing.
5. If any statement throws, SQLite undoes the others, and the Effect fails. The failure is turned into a defect by `Effect.orDie`, like every other disk problem.
6. The counter `seq` is set to `next` only after the transaction has committed. A delivery that is undone does not use up a number, so the log has no gap.
7. `pending` is a `count(*)` over this session's inbox rows.
8. `Session.of` now returns the three new members next to the old ones.

A short script shows the three methods together. It is a throwaway check and not part of the project: run it from a terminal in the `my-agent` folder, and it saves nothing as a file. It admits two prompts, delivers one, and prints the counts and the log after each move:

```bash
bun -e '
import { Effect } from "effect"
import { Session, SessionLive } from "./src/session"

const program = Effect.gen(function* () {
  const session = yield* Session
  yield* session.admit("List the files")
  yield* session.admit("Read notes/todo.txt")
  console.log("pending after two admits:", yield* session.pending)
  console.log("log after two admits:    ", (yield* session.events).length, "events")
  console.log("delivered:", yield* session.deliver)
```

```ts
import { toHistory } from "./history"
import type { Message } from "./messages"
import { SessionEvent } from "./session-event"
import { EventTable, InboxTable } from "./db/schema"

// What the agent needs from its session: accept prompts, append facts, and read the facts back.
export class Session extends Context.Service<
  Session,
  {
    readonly id: string
    // Saves a prompt in the inbox. From this moment it survives a restart, whether or not the model ever sees it.
    readonly admit: (text: string) => Effect.Effect<void>
    // Moves the oldest prompt out of the inbox and into the log as a `prompt` event, in one indivisible act.
    // Returns its text, or undefined when the inbox is empty.
    readonly deliver: Effect.Effect<string | undefined>
    // How many prompts wait in the inbox.
    readonly pending: Effect.Effect<number>
    readonly append: (event: SessionEvent) => Effect.Effect<void>
    // Every call reads the log again.
    readonly events: Effect.Effect<SessionEvent[], SessionCorrupt>
    readonly history: Effect.Effect<Message[], SessionCorrupt>
  }
>()("@agent/Session") {}

const migrationsFolder = new URL("../drizzle", import.meta.url).pathname
const decode = Schema.decodeUnknownEffect(SessionEvent)
const encode = Schema.encodeSync(SessionEvent)

// The real session: a SQLite file. Building the layer opens the file and applies the migrations;
// the end of the program closes it. A disk failure is a defect, not something the agent can handle.
export const SessionLive = (options: { path: string; id: string }) =>
  Layer.effect(
    Session,
    Effect.gen(function* () {
      const db = yield* SQLiteBunDrizzle.makeWithDefaults()
      yield* migrate(db, { migrationsFolder })

      const thisSession = eq(EventTable.session_id, options.id)
      const thisInbox = eq(InboxTable.session_id, options.id)

      // The numbering continues where the log stops. One process writes a session, so it can count for itself.
      const [last] = yield* db.select({ seq: max(EventTable.seq) }).from(EventTable).where(thisSession)
      let seq = last?.seq ?? 0

      // A row that no longer matches the schema stops the read and says which event it was.
      const readEvent = (row: typeof EventTable.$inferSelect) =>
        decode(row.data).pipe(
          Effect.mapError((error) => new SessionCorrupt({ session: options.id, seq: row.seq, problem: error.message })),
        )

      const events = db.select().from(EventTable).where(thisSession).orderBy(asc(EventTable.seq)).pipe(
        Effect.flatMap(Effect.forEach(readEvent)),
        Effect.catchTag("EffectDrizzleQueryError", Effect.die),
      )

      const append = (event: SessionEvent) =>
        Effect.suspend(() =>
          db.insert(EventTable).values({ session_id: options.id, seq: ++seq, type: event.type, data: encode(event) }),
        ).pipe(Effect.asVoid, Effect.orDie)

      const admit = (text: string) =>
        db.insert(InboxTable).values({ session_id: options.id, text }).pipe(Effect.asVoid, Effect.orDie)

      // Deleting the inbox row and inserting the `prompt` event happen in one transaction: both take effect,
      // or neither does. A crash between the two statements cannot lose the prompt or deliver it twice.
      const deliver = Effect.suspend(() => {
        const next = seq + 1
        return db
          .transaction((tx) =>
            Effect.gen(function* () {
              const [oldest] = yield* tx.select().from(InboxTable).where(thisInbox).orderBy(asc(InboxTable.id)).limit(1)
              if (!oldest) return undefined
              yield* tx.delete(InboxTable).where(eq(InboxTable.id, oldest.id))
              yield* tx
                .insert(EventTable)
                .values({ session_id: options.id, seq: next, type: "prompt", data: encode({ type: "prompt", text: oldest.text }) })
              return oldest.text
            }),
          )
          .pipe(
            // The number is used up only once the transaction has committed.
            Effect.tap((text) =>
              Effect.sync(() => {
                if (text !== undefined) seq = next
              }),
            ),
            Effect.orDie,
          )
      })

      const pending = db.select({ waiting: count() }).from(InboxTable).where(thisInbox).pipe(
        Effect.map(([row]) => row?.waiting ?? 0),
        Effect.orDie,
      )

      return Session.of({ id: options.id, admit, deliver, pending, append, events, history: Effect.map(events, toHistory) })
    }).pipe(Effect.orDie),
  ).pipe(Layer.provide(SqliteClient.layer({ filename: options.path }).pipe(Layer.orDie)))
```

### Step 4: A terminal that two readers can share

The reader will ask for lines at the same time as a tool may ask for an approval, so the terminal needs the router from decision 6. The router is a small piece of plain code with no Effect services in it, and it gets its own file. Create `src/lines.ts`. It starts with two imports, then the type that says what the router offers, and then `makeLines`, which builds one:

```ts
import { Effect } from "effect"
import { InputClosed } from "./errors"

// Hands the lines the user types to whoever is asking for one.
// - A line that arrives while nobody is asking waits, and the next question receives it.
// - When several questions are open, the newest one receives the line: it was printed last, so it is the one being answered.
// - When input ends, every open question fails with InputClosed, and so does every later one once the waiting lines are used up.
export interface Lines {
  readonly push: (line: string) => void
  readonly end: () => void
  readonly next: Effect.Effect<string, InputClosed>
}

export const makeLines = (): Lines => {
  const waiting: string[] = []
  const asking: Array<(answer: Effect.Effect<string, InputClosed>) => void> = []
  let ended = false

  return {
    push: (line) => {
      const asker = asking.pop()
      if (asker) asker(Effect.succeed(line))
      else waiting.push(line)
    },
    end: () => {
      ended = true
      for (const asker of asking.splice(0)) asker(Effect.fail(new InputClosed()))
    },
    next: Effect.callback<string, InputClosed>((resume) => {
      const line = waiting.shift()
      if (line !== undefined) return resume(Effect.succeed(line))
      if (ended) return resume(Effect.fail(new InputClosed()))
      asking.push(resume)
      // A question that is interrupted stops asking, so it cannot take a line meant for the next one.
      return Effect.sync(() => {
        const index = asking.indexOf(resume)
        if (index >= 0) asking.splice(index, 1)
      })
    }),
  }
}
```

1. `Lines` has three parts. `push` is called with each line that was typed, `end` is called once when the input ends, and `next` is an Effect that produces one line, or fails with `InputClosed`.
2. `waiting` holds lines that arrived when nobody was asking. `asking` holds one callback for each open question, oldest first. `ended` remembers that the input is over.
3. `push` takes the newest open question with `asking.pop()` and gives it the line. If no question is open, the line goes to the back of `waiting`.
4. `end` marks the input as ended and fails every open question with `InputClosed`, the error that [Part 5](/posts/why-effect/) introduced for this case.
5. `next` first looks at `waiting`, so lines typed ahead are used in order. After that, if the input has ended, it fails. Otherwise it registers itself as an open question.
6. `Effect.callback` builds an Effect from a function that calls `resume` later. The Effect it returns from the function is the cleanup, which runs if the question is interrupted. It removes the question from `asking`, so an interrupted question cannot take a line that belongs to the next one.

Now `src/terminal.ts`, which exists from [Part 8](/posts/the-session-as-an-event-log/), uses the router. Two changes are needed. In the imports at the top, the readline import changes from `"node:readline/promises"` to `"node:readline"`, since the callback style is all that is needed now, and an import for the router is added after the one from `./errors`. Replace the last two import lines, the readline and `./errors` ones, with these three:

```ts

```

Then replace the whole `TerminalLive` definition, from its comment to the closing parenthesis, with the version below. The `Terminal` class above it stays as it is. `TerminalLive` feeds the router with readline's lines and keeps the three methods:

```ts
// The real terminal. Building the layer starts reading standard input; the end of the program stops it.
// readline only cuts the input into lines. It is given no output, so the terminal itself echoes what is typed,
// and a reply that is printed while the user types cannot disturb a line readline is redrawing.
export const TerminalLive = Layer.effect(
  Terminal,
  Effect.gen(function* () {
    const lines = makeLines()

    yield* Effect.acquireRelease(
      Effect.sync(() => {
        const rl = createInterface({ input: process.stdin })
        rl.on("line", lines.push)
        rl.on("close", lines.end)
        return rl
      }),
      (rl) => Effect.sync(() => rl.close()),
    )

    return Terminal.of({
      ask: (prompt) => Effect.sync(() => void process.stdout.write(prompt)).pipe(Effect.andThen(lines.next)),
      say: (line) => Effect.sync(() => console.log(line)),
      write: (text) => Effect.sync(() => void process.stdout.write(text)),
    })
  }),
)
```

1. `makeLines()` creates one router for the whole program. The promise that [Part 8](/posts/the-session-as-an-event-log/) built to turn the end of input into a rejection is gone, because the router already fails its questions when the input ends.
2. `Effect.acquireRelease` opens readline when the layer is built and closes it when the program ends, as before. The readline interface is created with only `input`. That makes it cut the input into lines and nothing else: it does not echo, and it does not redraw the line. The terminal itself shows what is typed.
3. Each `line` event goes to `lines.push`, and the `close` event, which Ctrl-D and the end of piped input both produce, goes to `lines.end`.
4. `ask` prints the prompt and then waits for `lines.next`. The prompt is printed by the terminal service and not by readline, so a prompt printed while a reply streams does not clash with readline's own redrawing.
5. `say` and `write` are as in [Part 8](/posts/the-session-as-an-event-log/). Without readline's line editing, the arrow keys do not recall earlier lines. The terminal's own editing, such as Backspace, still works.

```ts
import { Effect } from "effect"
import { InputClosed } from "./errors"

// Hands the lines the user types to whoever is asking for one.
// - A line that arrives while nobody is asking waits, and the next question receives it.
// - When several questions are open, the newest one receives the line: it was printed last, so it is the one being answered.
// - When input ends, every open question fails with InputClosed, and so does every later one once the waiting lines are used up.
export interface Lines {
  readonly push: (line: string) => void
  readonly end: () => void
  readonly next: Effect.Effect<string, InputClosed>
}

export const makeLines = (): Lines => {
  const waiting: string[] = []
  const asking: Array<(answer: Effect.Effect<string, InputClosed>) => void> = []
  let ended = false

  return {
    push: (line) => {
      const asker = asking.pop()
      if (asker) asker(Effect.succeed(line))
      else waiting.push(line)
    },
    end: () => {
      ended = true
      for (const asker of asking.splice(0)) asker(Effect.fail(new InputClosed()))
    },
    next: Effect.callback<string, InputClosed>((resume) => {
      const line = waiting.shift()
      if (line !== undefined) return resume(Effect.succeed(line))
      if (ended) return resume(Effect.fail(new InputClosed()))
      asking.push(resume)
      // A question that is interrupted stops asking, so it cannot take a line meant for the next one.
      return Effect.sync(() => {
        const index = asking.indexOf(resume)
        if (index >= 0) asking.splice(index, 1)
      })
    }),
  }
}
```

```ts
// - The reader asks for a line, saves it in the inbox, and asks again, even while a turn is running.
// - The worker finishes an interrupted turn, then delivers one prompt at a time and runs its turn.
// The reader rings a bell after each prompt. The ring carries no prompt: it only tells the worker to look at the inbox.
export const repl = Effect.gen(function* () {
  const terminal = yield* Terminal
  const session = yield* Session

  // A turn that fails is recorded as failed, so the next prompt starts from a consistent history.
  const failed = (label: string, reason: string) =>
    session.append({ type: "turn-failed", reason }).pipe(Effect.andThen(terminal.say(`[${label}] ${reason}`)))
  const guarded = <R>(work: Effect.Effect<void, ProviderError | SessionCorrupt | InputClosed, R>) =>
    work.pipe(
      Effect.catchTag("ProviderError", (error) => failed("provider error", error.message)),
      Effect.catchDefect((defect) => failed("bug", messageOf(defect))),
    )

  // At most one ring waits at a time: two rings in a row mean the same thing as one.
  const wake = yield* Queue.dropping<void>(1)
  let inputEnded = false

  const reader = Effect.gen(function* () {
    while (true) {
      const input = yield* terminal.ask("You: ")
      yield* session.admit(input)
      yield* terminal.say("[queued]")
      yield* Queue.offer(wake, undefined)
    }
  }).pipe(
    Effect.catchTag("InputClosed", () => Effect.sync(() => void (inputEnded = true))),
    Effect.andThen(Queue.offer(wake, undefined)),
  )

  // What the last run left in the inbox, counted before the reader can add anything.
  const left = yield* session.pending
  if (left > 0) yield* terminal.say(`[${queued(left)} from an earlier run]`)

  yield* Effect.forkChild(reader)
  yield* guarded(resume)

  while (true) {
    // Read before delivering: a prompt admitted before the input ended is then always found by the delivery below.
    const ended = inputEnded
    if ((yield* session.deliver) !== undefined) {
      yield* guarded(run)
      continue
    }
    if (ended) return
    yield* Queue.take(wake)
  }
})
```

```ts
export const scriptedTerminal = (answers: Array<string | Promise<string>>, confirmations: string[] = []) => {
  const output: string[] = []
  const writes: string[] = []
  const queue = [...answers]
  const confirm = [...confirmations]
  let pending = "" // text written since the last line ended
  const layer = Layer.succeed(
    Terminal,
    Terminal.of({
      ask: (prompt) =>
        Effect.suspend(() => {
          output.push(pending + prompt)
          pending = ""
          const next = (prompt.startsWith("Allow") ? confirm : queue).shift()
          if (next === undefined) return Effect.fail(new InputClosed())
          return typeof next === "string" ? Effect.succeed(next) : Effect.promise(() => next)
        }),
      say: (line) =>
        Effect.sync(() => {
          output.push(pending + line)
          pending = ""
        }),
      write: (text) =>
        Effect.sync(() => {
          writes.push(text)
          pending += text
        }),
    }),
  )
  return { layer, output, writes }
}
```

### Possible extensions

Three small additions fit the design and are not built here:

- **Idempotent admission.** `admit` could take an id from the caller and ignore a second admission with the same id. A client that retries a submit after a timeout would then not queue the same prompt twice. OpenCode works this way: reusing an inbox item id is idempotent, and the first admission wins.
- **Cancelling a waiting prompt.** Since the inbox is a table, a prompt can be removed from it before it is delivered. A `cancel(id)` that deletes the row, and a way to list the rows with their ids, would be enough.
- **A line editor.** The terminal could redraw the `You: ` prompt and the text typed so far after each piece of output, so a reply no longer lands in the middle of a line being typed. That is a terminal user interface feature, and it would also bring back the arrow keys that readline's editing used to provide.

### OpenCode does more

Three things are left out on purpose. **Execution claims:** OpenCode writes a claim when a turn starts and releases it when the turn ends, so a claim that is still there on startup means a process died in the middle of a turn. The agent here recognises an unfinished turn from the shape of the log, with `unansweredCalls` from [Part 8](/posts/the-session-as-an-event-log/), which covers one process and one session. **Steering:** a prompt can be delivered at a step boundary inside a running turn, as decision 4 describes. **An attempts budget:** a turn that keeps killing the process would be resumed forever, so OpenCode counts the resumes of each turn and, after `maxAttempts` (10 by default), ends the turn as aborted instead ([session/execution/restart.ts](https://github.com/anomalyco/opencode/blob/97be25f046/packages/core/src/session/execution/restart.ts#L26-L34)). The same file states the guarantee: recovery is at-least-once, and local coordination prevents concurrent drains but not repeated external side effects after a crash ([comment](https://github.com/anomalyco/opencode/blob/97be25f046/packages/core/src/session/execution/restart.ts#L53-L54)).

```ts
import { Effect } from "effect"
import { InputClosed } from "./errors"

// Hands the lines the user types to whoever is asking for one.
// - A line that arrives while nobody is asking waits, and the next question receives it.
// - When several questions are open, the newest one receives the line: it was printed last, so it is the one being answered.
// - When input ends, every open question fails with InputClosed, and so does every later one once the waiting lines are used up.
export interface Lines {
  readonly push: (line: string) => void
  readonly end: () => void
  readonly next: Effect.Effect<string, InputClosed>
}

export const makeLines = (): Lines => {
  const waiting: string[] = []
  const asking: Array<(answer: Effect.Effect<string, InputClosed>) => void> = []
  let ended = false

  return {
    push: (line) => {
      const asker = asking.pop()
      if (asker) asker(Effect.succeed(line))
      else waiting.push(line)
    },
    end: () => {
      ended = true
      for (const asker of asking.splice(0)) asker(Effect.fail(new InputClosed()))
    },
    next: Effect.callback<string, InputClosed>((resume) => {
      const line = waiting.shift()
      if (line !== undefined) return resume(Effect.succeed(line))
      if (ended) return resume(Effect.fail(new InputClosed()))
      asking.push(resume)
      // A question that is interrupted stops asking, so it cannot take a line meant for the next one.
      return Effect.sync(() => {
        const index = asking.indexOf(resume)
        if (index >= 0) asking.splice(index, 1)
      })
    }),
  }
}
```

```ts
      part: { type: "tool-result", id: call.id, name: call.name, result: { type: "error", value: interrupted } },

// - The reader asks for a line, saves it in the inbox, and asks again, even while a turn is running.
// - The worker finishes an interrupted turn, then delivers one prompt at a time and runs its turn.
// The reader rings a bell after each prompt. The ring carries no prompt: it only tells the worker to look at the inbox.

  // A turn that fails is recorded as failed, so the next prompt starts from a consistent history.
  const failed = (label: string, reason: string) =>
    session.append({ type: "turn-failed", reason }).pipe(Effect.andThen(terminal.say(`[${label}] ${reason}`)))

    work.pipe(

      Effect.catchDefect((defect) => failed("bug", messageOf(defect))),
    )

  const wake = yield* Queue.dropping<void>(1)
  let inputEnded = false

  const reader = Effect.gen(function* () {
    while (true) {
      const input = yield* terminal.ask("You: ")
      yield* session.admit(input)
      yield* terminal.say("[queued]")
      yield* Queue.offer(wake, undefined)
    }
  }).pipe(
    Effect.catchTag("InputClosed", () => Effect.sync(() => void (inputEnded = true))),
    Effect.andThen(Queue.offer(wake, undefined)),
  )

  // What the last run left in the inbox, counted before the reader can add anything.
  const left = yield* session.pending
  if (left > 0) yield* terminal.say(`[${queued(left)} from an earlier run]`)

  yield* Effect.forkChild(reader)
  yield* guarded(resume)

  while (true) {

    const ended = inputEnded
    if ((yield* session.deliver) !== undefined) {
      yield* guarded(run)
      continue
    }
    if (ended) return
    yield* Queue.take(wake)
  }
```

```ts
  const writes: string[] = []
  const queue = [...answers]
  const confirm = [...confirmations]

  const layer = Layer.succeed(
    Terminal,
    Terminal.of({
      ask: (prompt) =>
        Effect.suspend(() => {
          output.push(pending + prompt)
          pending = ""
          const next = (prompt.startsWith("Allow") ? confirm : queue).shift()
          if (next === undefined) return Effect.fail(new InputClosed())
          return typeof next === "string" ? Effect.succeed(next) : Effect.promise(() => next)

          output.push(pending + line)
          pending = ""
        }),
      write: (text) =>
        Effect.sync(() => {
          writes.push(text)
          pending += text
        }),
    }),
  )
```

```ts
      intruder.run(`insert into event (session_id, seq, type, data) values ('s', 1, 'prompt', '{"type":"prompt","text":"intruder"}')`)
      intruder.close()
      const exit = yield* Effect.exit(session.deliver)
      return { failed: Exit.isFailure(exit), pending: yield* session.pending }
    }).pipe(Effect.provide(SessionLive({ path, id: "s" }))),
  )

  expect(outcome).toEqual({ failed: true, pending: 1 })
})
```

`test/resume.test.ts`

```ts
import { afterEach, beforeEach, describe, expect, test } from "bun:test"
import { Effect, Layer, Schema } from "effect"
import { mkdtemp, rm } from "node:fs/promises"
import { tmpdir } from "node:os"
import { join } from "node:path"
import { repl } from "../src/agent"
import type { SessionEvent } from "../src/session-event"
import { Session, SessionLive } from "../src/session"
import { defineTool, Tools } from "../src/tool"
import { callTool, reply, scriptedModel, scriptedTerminal } from "./fakes"

// A crash leaves the log as it was at the moment the process died. These tests write that log with
// `append`, close the file, and start the agent again on it.
let dir: string
beforeEach(async () => {
  dir = await mkdtemp(join(tmpdir(), "agent-session-"))
})
afterEach(() => rm(dir, { recursive: true, force: true }))

const ran: string[] = []
const echo = defineTool({
  name: "echo",
  description: "Returns its text.",
  input: Schema.Struct({ text: Schema.String }),
  execute: async ({ text }) => (ran.push(text), text),
})

const prompt = (text: string): SessionEvent => ({ type: "prompt", text })
const calls = (...ids: string[]): SessionEvent => ({
  type: "step-finished",
  message: { role: "assistant", content: ids.map((id) => ({ type: "tool-call", id, name: "echo", input: { text: id } })) },
  finish: "tool-calls",
})
const result = (id: string): SessionEvent => ({
  type: "tool-result",
  part: { type: "tool-result", id, name: "echo", result: { type: "text", value: id } },
})

// Process one: the events that were written before the crash, and the prompts that were still in the inbox.
const crashAfter = (events: SessionEvent[], inbox: string[] = []) =>
  Effect.runPromise(
    Effect.gen(function* () {
      const session = yield* Session
      for (const event of events) yield* session.append(event)
      for (const text of inbox) yield* session.admit(text)
    }).pipe(Effect.provide(SessionLive({ path: join(dir, "agent.db"), id: "s" }))),
  )

// Process two: a new agent on the same file. No input, so it only finishes what it finds.
const restart = async (modelSteps: Parameters<typeof scriptedModel>[0]) => {
  const model = scriptedModel(modelSteps)
  const terminal = scriptedTerminal([])
  const layers = Layer.mergeAll(model.layer, terminal.layer, Layer.succeed(Tools, [echo]), SessionLive({ path: join(dir, "agent.db"), id: "s" }))
  const events = await Effect.runPromise(
    Effect.gen(function* () {
      yield* repl
      return yield* (yield* Session).events
    }).pipe(Effect.provide(layers)),
  )
  return { events, requests: model.requests, output: terminal.output }
}

describe("resuming a session", () => {
  test("answers a call that has no result with an error and never runs it again", async () => {
    ran.length = 0
    await crashAfter([prompt("go"), calls("a", "b"), result("a")])

    const { events, requests, output } = await restart([reply("Understood.")])

    expect(output[0]).toBe("[resuming session s]")
    expect(ran).toEqual([])
    const tool = requests[0]?.at(-1)
    expect(tool?.role).toBe("tool")
    expect(tool?.content.map((part) => (part.type === "tool-result" ? [part.id, part.result.type] : []))).toEqual([
      ["a", "text"],
      ["b", "error"],
    ])
    expect(JSON.stringify(tool)).toContain("stopped before this tool finished")
    expect(events.map((event) => event.type)).toEqual(["prompt", "step-finished", "tool-result", "tool-result", "step-finished"])
  })

  test("continues a turn that stopped right after the prompt", async () => {
    await crashAfter([prompt("hello")])

    const { requests, output } = await restart([reply("Hi.")])

    expect(output).toContain("Agent: Hi.")
    expect(requests[0]?.map((message) => message.role)).toEqual(["user"])
  })

  test("continues a turn that stopped between the last result and the next step", async () => {
    await crashAfter([prompt("go"), calls("a"), result("a")])

    const { requests } = await restart([reply("Done.")])

    expect(requests[0]?.map((message) => message.role)).toEqual(["user", "assistant", "tool"])
  })

  test("leaves a finished turn alone", async () => {
    await crashAfter([prompt("hi"), { type: "step-finished", message: { role: "assistant", content: [{ type: "text", text: "Hello." }] }, finish: "stop" }])

    const { requests, output } = await restart([])

    expect(requests).toEqual([])
    expect(output.join("\n")).not.toContain("resuming")
  })

  test("leaves a failed turn alone", async () => {
    await crashAfter([prompt("hi"), { type: "turn-failed", reason: "connection reset" }])

    const { requests, output } = await restart([])

    expect(requests).toEqual([])
    expect(output.join("\n")).not.toContain("resuming")
  })

  test("a resumed turn that calls a tool runs it like any other", async () => {
    ran.length = 0
    await crashAfter([prompt("go")])

    await restart([callTool("c9", "echo", { text: "again" }), reply("Done.")])

    expect(ran).toEqual(["again"])
  })

  test("runs the prompts that were still in the inbox, in order", async () => {
    await crashAfter([], ["one", "two"])

    const { events, output } = await restart([reply("A."), reply("B.")])

    expect(output).toContain("[2 queued prompts from an earlier run]")
    expect(events.map((event) => (event.type === "prompt" ? event.text : event.type))).toEqual(["one", "step-finished", "two", "step-finished"])
  })

  test("finishes the interrupted turn before it delivers the next prompt", async () => {
    await crashAfter([prompt("first")], ["second"])

    const { events, requests, output } = await restart([reply("A."), reply("B.")])

    expect(output.slice(0, 2)).toEqual(["[1 queued prompt from an earlier run]", "[resuming session s]"])
    expect(requests[0]?.map((message) => message.role)).toEqual(["user"])
    expect(events.map((event) => (event.type === "prompt" ? event.text : event.type))).toEqual(["first", "step-finished", "second", "step-finished"])
  })

  test("says nothing about the inbox when it is empty", async () => {
    await crashAfter([prompt("hi"), { type: "step-finished", message: { role: "assistant", content: [{ type: "text", text: "Hello." }] }, finish: "stop" }])

    const { output } = await restart([])

    expect(output.join("\n")).not.toContain("queued prompt")
  })
})
```
